YAML Dublin Core and Markdown

Closing Markdown's metadata gap with Dublin Core and YAML frontmatter

In my last post, I made the case that Markdown's plain-text simplicity gives it real staying power as a preservation format — human-readable, software-agnostic, and likely to remain accessible decades from now. But I also flagged a significant weakness: Markdown has no native mechanism for metadata. No author field, no date, no rights statement, no subject headings. For archivists, that's not a minor inconvenience — it's a dealbreaker. A document without provenance is just an orphan. This post is about how we can fix that gap using two technologies that already exist, work well together, and align with established archival practice: YAML frontmatter and Dublin Core.

Markdown was never designed to describe itself

John Gruber created Markdown in 2004 as a text-to-HTML conversion tool for web writers. Its purpose was formatting content — paragraphs, headers, links, emphasis — not describing it. The original specification says nothing about metadata. Neither does CommonMark, the most serious effort to formalize Markdown syntax. John MacFarlane, CommonMark's creator, stated directly on the project's discussion forum that "front matter is not going to be part of the spec," adding that applications should handle metadata extraction on their own. The Library of Congress lists plain text as an "acceptable" digital preservation format, but not a "preferred" one, partly because it lacks self-documenting metadata. The Digital Preservation Coalition makes the same point: ideally, formats should "allow for the inclusion of internal metadata" so content and description are never separated.

So if we want to use Markdown in archival workflows — and there are compelling reasons to do so — we need a metadata layer.

YAML frontmatter fills the gap, imperfectly but practically

YAML frontmatter is a block of structured key-value metadata placed at the very top of a Markdown file, fenced between triple dashes (---). Jekyll, the static site generator, popularized this convention around 2008, and it has since been adopted by Hugo, Pandoc, Obsidian, Gatsby, Eleventy, and dozens of other tools. It looks like this: a few lines of human-readable data — title, author, date, tags — sitting above the document content, parseable by machines but perfectly legible to a person reading the raw file.

The critical thing to understand is that YAML frontmatter is a convention, not a specification. GitHub's own documentation describes it as "an authoring convention popularized by Jekyll." It is not part of CommonMark, not part of any Markdown standard, and different tools handle it differently. That matters, and I'll return to it. But as a practical, widely supported method for embedding metadata in plain-text files, it is the best option we have.

Dublin Core gives YAML frontmatter a proper vocabulary

The missing piece is a controlled vocabulary — a standard set of metadata fields with agreed-upon definitions. This is exactly what the Dublin Core Metadata Element Set provides. Developed in 1995 at a workshop in Dublin, Ohio, and now maintained by the Dublin Core Metadata Initiative under ASIS&T, Dublin Core defines 15 core elements: Title, Creator, Subject, Description, Publisher, Contributor, Date, Type, Format, Identifier, Source, Language, Relation, Coverage, and Rights. It is codified as ISO 15836-1:2017, required as the baseline format by OAI-PMH (the protocol underpinning most institutional repository harvesting), and used natively by platforms like DSpace, Fedora, and Omeka. Each element is optional, repeatable, and intentionally broad enough to describe resources across domains.

When you combine Dublin Core's standardized vocabulary with YAML frontmatter's embeddable structure, you get something genuinely useful: a self-describing, plain-text archival document with metadata that any archivist or system can interpret.

Institutions are already doing this

This is not purely theoretical. Chris Diaz at Northwestern University Libraries published a workflow in the Code4Lib Journal (Issue 42, 2018) that explicitly maps YAML frontmatter fields in Jekyll-based Markdown files to Dublin Core <meta> tags in HTML output, alongside Google Scholar and Open Graph metadata — all generated from the same YAML source. Northwestern's Lantern project, an open-source Pandoc-based OER publishing toolkit documented in Code4Lib Journal Issue 53, uses a metadata.yml file with bibliographic fields that directly parallel Dublin Core elements. At Virginia Tech, the Caleb Pungowiyi Papers Rematriation Project used Obsidian — which stores notes as Markdown with YAML frontmatter — to create structured archival metadata for Indigenous cultural materials. Even DCMI itself migrated its website to Hugo with Markdown and YAML in 2017.

Pandoc is the critical bridge

Pandoc makes this approach genuinely powerful by providing explicit, built-in Dublin Core support. When converting Markdown to EPUB, Pandoc maps YAML metadata fields directly to Dublin Core elements in the OPF package file: title becomes <dc:title>, creator becomes <dc:creator>, rights becomes <dc:rights>, and so on across all 15 elements. Pandoc also supports structured values — you can specify identifier schemes (ISBN, DOI, OCLC), creator roles (author, editor using MARC relators), and subject authorities (LCSH, DDC). This means a single YAML frontmatter block can serve as the metadata source for HTML pages, PDF documents, and standards-compliant EPUBs, all from one Markdown file.

The limitations are real and should be stated honestly

YAML frontmatter has no formal validation mechanism. There is no schema enforcement ensuring your Dublin Core fields are correctly named or properly formatted. The YAML specification itself is notoriously tricky — the "Norway problem," where the country code NO is silently parsed as boolean false, still persists in major parsing libraries as of early 2026. Different tools expect different field names (author vs. creator, date vs. published), and a CommonMark parser that doesn't recognize frontmatter will interpret the opening --- as a thematic break, mangling your metadata entirely. This approach is a pragmatic bridge, not a replacement for METS, PREMIS, or EAD in formal preservation systems.

A practical starting point for archivists

Here is a sample YAML frontmatter block implementing Dublin Core elements that I would recommend as a starting template for archival Markdown documents:

---
dc.title: "Correspondence of Maria Torres, 1943–1947"
dc.creator: "Torres, Maria"
dc.subject:
  - "World War, 1939-1945 -- Personal narratives"
  - "Mexican Americans -- Correspondence"
dc.description: "Letters written by Maria Torres to family members during WWII."
dc.publisher: "University Special Collections"
dc.date: "1943/1947"
dc.type: "Text"
dc.format: "text/markdown"
dc.identifier: "SC-2024-0047"
dc.language: "en"
dc.rights: "This material is in the public domain."
dc.source: "Maria Torres Papers, Box 3, Folder 12"
dc.coverage: "United States -- Texas"
---

Using the dc. prefix is deliberate — it signals to any reader or downstream system that these fields follow the Dublin Core schema rather than an ad hoc convention. Quote your string values. Use ISO 8601 or EDTF for dates. Use LCSH or AAT for subject terms where possible. And document your local conventions in a README alongside your files, because without a formal schema, human documentation is your validation layer.

Markdown's durability as plain text is real. Dublin Core's interoperability as a metadata standard is proven. YAML frontmatter's role as a bridge between them is imperfect but practical, widely supported, and — for many of us working in special collections — immediately usable. The formal preservation infrastructure of our institutions will continue to rely on XML-based standards and repository platforms. But for the working notes, transcriptions, finding aid drafts, and descriptive documents that live in our daily workflows, embedding Dublin Core in YAML is a small discipline that makes those files significantly more discoverable, portable, and archivally responsible.
