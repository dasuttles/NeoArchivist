Markdown in Archives

Posted on Wed 25 February 2026 in misc

Markdown — the lightweight markup language created for bloggers in 2004 — has become one of the most preservation-friendly formats in a digital archivist's toolkit. Its radical simplicity solves a problem that keeps archivists up at night: how do you ensure documents remain readable not just next year, but in fifty or a hundred years? Across the profession, from the National Archives to university special collections, institutions are adopting Markdown for documentation, digital collections, and even preservation planning itself. The format isn't perfect — its lack of native metadata and flavor fragmentation pose real challenges — but its alignment with core preservation principles makes it impossible to ignore.

As someone who spends their days in university special collections wrestling with born-digital accessions, legacy file formats, and the eternal question of "will anyone be able to open this in 2075?", I've become a quiet evangelist for Markdown. Here's why — and where the limits are.

A format born from frustration with formatting

John Gruber released Markdown in 2004, with significant input from the late Aaron Swartz. Gruber, a technology writer and designer behind the Daring Fireball blog, created it out of sheer frustration with HTML. He'd been writing for the web and found HTML "ugly" and "really hard to proofread." His solution was elegantly constrained: a plain text syntax that looks like what it means. Asterisks around a word look like *emphasis*. Hash marks before a line look like a heading. As Gruber wrote in his original specification, "a Markdown-formatted document should be publishable as-is, as plain text, without looking like it's been marked up with tags or formatting instructions."

That design philosophy — readability above all else — turns out to be profoundly aligned with digital preservation principles. Gruber drew his inspiration from plain text email conventions, the idea being that the format of the source file should be human-readable even without rendering software. He described the distinction crisply: "HTML is a publishing format; Markdown is a writing format." Two decades later, Markdown has exploded far beyond blogging. GitHub, Reddit, Stack Exchange, Discord, and hundreds of documentation platforms use it as their default authoring format. The CommonMark specification, launched in 2014 by John MacFarlane (creator of Pandoc) and Jeff Atwood (co-founder of Stack Overflow), has brought more formal standardization, with over 500 conformance tests in the current spec.

For archivists, none of this history matters as much as one brute fact: a Markdown file written in 2004 is still perfectly readable today in any text editor on any operating system. No special software. No license. No rendering engine. Just characters on a screen.

Why the Library of Congress cares about transparency (and you should too)

The digital preservation community has spent decades developing frameworks for evaluating format sustainability, and plain text formats like Markdown perform remarkably well against these criteria. The Library of Congress identifies seven sustainability factors for digital formats: Disclosure, Adoption, Transparency, Self-documentation, External Dependencies, Impact of Patents, and Technical Protection Mechanisms. Markdown scores excellently on six of these seven.

Its transparency is unmatched — the LC defines this as "openness to direct analysis with basic and non-proprietary tools," and there is no format more transparent than plain text. Its external dependencies are essentially zero. No patents encumber it. No DRM can be applied to it. Its specification is openly published. Its adoption is massive and growing. The only factor where Markdown genuinely stumbles is self-documentation — the ability to embed metadata needed to understand context and provenance. Plain text has no native mechanism for Dublin Core elements, XMP metadata, or structured descriptive information. This is precisely why the LC's Recommended Formats Statement lists plain text as "acceptable" rather than "preferred" for digital textual works, placing it below XML-based formats and PDF/A, which mandate embedded metadata.

The OAIS Reference Model (ISO 14721), the foundational framework for digital preservation systems, reinforces why plain text matters through a different lens. OAIS emphasizes that archived content should be "independently understandable" by a designated community, and that preservation planning must account for format obsolescence and migration. Plain text minimizes what OAIS calls "Representation Information" — the supplementary data needed to make a bitstream intelligible. A UTF-8 text file needs almost no Representation Information. A .docx file needs a great deal. The NDSA Levels of Digital Preservation, which build on OAIS principles, explicitly recommend open, non-proprietary formats and point to the LC's sustainability factors as guidance. The message across these frameworks is consistent: the simpler and more open the format, the lower the long-term preservation risk.

From finding aids to processing manuals, Markdown is already here

Archival description remains dominated by Encoded Archival Description (EAD), an XML standard with 146 elements maintained by the Library of Congress and the Society of American Archivists. Markdown can't replace EAD — it lacks the semantic granularity needed for hierarchical, multi-level finding aids with controlled vocabularies and linking. No direct Markdown-to-EAD conversion tool exists. But that's not really where Markdown is making its mark in archival practice.

Where Markdown has genuinely transformed archival workflows is in documentation, SOPs, and institutional knowledge management — the operational backbone that keeps archives running. The New York Public Library maintains its entire Archival Processing Manual as Markdown files on GitHub Pages, covering everything from accessioning to inclusive cataloging to peer review. The Canadian Centre for Architecture publishes its born-digital archives processing manual on GitHub in Markdown, documenting workflows for stabilization, triage, arrangement, and description. The University of Denver's Special Collections does the same with its processing manual. These aren't experiments — they're production documentation systems used daily by working archivists.

The shift from Word documents on shared drives to Markdown files in Git repositories represents more than a format change. It's a philosophical shift toward treating documentation as versionable, diffable, collaborative infrastructure. When the Rockefeller Archive Center migrated their internal documentation to Markdown, staff reported that the conversion process itself forced "intentional and meaningful structure decisions" about headings and organization. The constraint of Markdown's simplicity became a feature, not a bug.

The Rockefeller Archive Center and NARA lead the way

The Rockefeller Archive Center (RAC) has become the gold standard for Markdown adoption in archival practice. Their documentation site at docs.rockarch.org is a static Jekyll site built entirely from Markdown files hosted on GitHub. Their blog migrated from WordPress to Jekyll, with posts converted to individual Markdown files using Pandoc. Their employee handbook lives on GitHub. Their main website is a Jekyll static site. The RAC even published a formal staff guide for learning Markdown, listing tools like Pandoc and Sublime Text for authoring. As one RAC processing archivist noted, their coding experience before joining had been "limited to EAD and TEI," and learning Markdown became a gateway to broader technical literacy.

Perhaps even more significant is NARA's adoption. The National Archives and Records Administration publishes its entire Digital Preservation Framework — including a risk matrix covering 700+ file formats and 16 Preservation Action Plans — as Markdown files on GitHub. In a 2025 blog post, NARA explained the reasoning: "Making the record category plans available as Markdown means that users can now see changes more easily," leveraging Git's commit history for transparent change tracking. This framework won the 2020 NDSA Innovation Award. NARA explicitly invites public comment through GitHub Issues, turning preservation policy into a collaborative, version-controlled process. When the nation's archives publishes its preservation strategy in Markdown on GitHub, the format has clearly moved beyond novelty.

Other notable examples include CollectionBuilder, an open-source framework from the University of Idaho Library funded by NEH and IMLS grants, which generates digital collection websites from metadata spreadsheets and Markdown content pages. Minicomp/Wax, developed at Columbia University Libraries, produces IIIF-compliant digital exhibitions from Markdown files. Even ArchivesSpace — the dominant archival management system — now authors its technical documentation in Markdown.

The honest comparison: Markdown versus Word and PDF/A

A fair preservation comparison requires acknowledging that each format optimizes for different things. Microsoft Word (.docx) is technically based on an ISO standard (ISO/IEC 29500, Office Open XML), and it supports rich embedded metadata including Dublin Core properties. But it's a complex XML-in-ZIP format that can't be casually read with a text editor, and full rendering fidelity typically depends on Microsoft's software. Format migration challenges are real — a May 2025 Office 365 update broke rendering of older .doc files, and anyone who has tried to open a 1990s WordPerfect document knows how quickly proprietary formats can become unreadable. As Dennis Tenen and Grant Wythoff wrote in their influential Programming Historian tutorial, "MS Word may go the way of Word Perfect in the future, but plain text will always remain easy to read, catalog, mine, and transform."

PDF/A (ISO 19005) is a more formidable comparison. It mandates XMP metadata, prohibits encryption, requires all fonts to be embedded, and is a preferred format at both the Library of Congress and NARA. It excels at preserving visual appearance. But PDF was designed as a page-layout language — it tells a printer where to place text elements, not what those elements mean. Content extraction and reuse from PDFs is notoriously unreliable. As one digital preservation researcher put it, PDF/A is "the end of the line for data." A 2017 iPRES paper titled "PDF/A considered harmful for digital preservation" highlighted how conversion to PDF/A can lose important semantics.

The fundamental trade-off is this: Markdown preserves content reusability perfectly but sacrifices formatting; PDF/A preserves visual appearance but locks content into a fixed layout. For archival documentation, processing manuals, and institutional knowledge — content that needs to evolve, be searched, be version-controlled, and survive indefinitely — Markdown's trade-offs are the right ones.

The real limitations archivists need to know about

Intellectual honesty demands acknowledging Markdown's genuine weaknesses in archival contexts. The flavor fragmentation problem is the most cited criticism. A CommonMark wiki page lists over 41 distinct Markdown flavors. GitHub Flavored Markdown, Pandoc Markdown, MultiMarkdown, and R Markdown all extend the base syntax in incompatible ways. Karl Voit's provocatively titled 2025 essay "Markdown Is a Disaster" warns that "if you have a large corpus of information written in some sort of Markdown, you will face more and more issues converting it to a more appropriate format." Eric Holscher, founder of Read the Docs, argues that flavor fragmentation creates a form of vendor lock-in that undermines Markdown's portability promise.

The metadata gap is arguably more consequential for archival work. Markdown has no native metadata system. YAML frontmatter — the --- delimited block at the top of many Markdown files — is a convention, not part of any specification, and it's inconsistently supported across tools. For a profession built on provenance, descriptive standards, and rights management, a format with no built-in way to express Dublin Core elements or link to authority files has obvious limitations.

Accessibility presents another concern. Markdown naturally produces clean semantic HTML — proper heading hierarchies, meaningful lists, structured paragraphs — which is inherently accessible. But it lacks mechanisms for ARIA roles, language attributes, complex table headers, or distinguishing decorative from informative images. The rendered accessibility depends entirely on the processing pipeline, not the format itself. And complex formatting — multi-column layouts, colored text, precise image positioning — simply isn't possible without dropping into raw HTML, which defeats the purpose.

Static sites, minimal computing, and the archival web to come

The future of Markdown in archives is inseparable from the static site movement and the broader philosophy of minimal computing. The Global Outlook::Digital Humanities (GO::DH) Minimal Computing working group, co-founded by Alex Gil at Columbia, advocates for digital scholarship built under constraints — limited bandwidth, minimal server dependencies, low maintenance overhead. Markdown plus a static site generator like Jekyll produces flat HTML files that require nothing more than a basic web server to deliver. No databases. No PHP. No security patches for WordPress plugins.

The Endings Project at the University of Victoria spent five years researching how to build lasting digital scholarship, and their conclusion was striking: "seemingly-retrograde mechanisms — in particular, static websites with no server dependency — allow projects to be easily archived, ported, and sustained." They found that the web technologies from the beginning of the web — HTML, CSS, JavaScript — are precisely the same ones still in use today. The first project archived at UVic Libraries under their new framework was one built with this static approach.

This matters because link rot is an existential threat to the archival web. Nearly 50% of links in Supreme Court opinions no longer work. A 2013 study found the median lifespan of web pages was just 9.3 years. Every WordPress site running on a MySQL database with PHP dependencies is a ticking clock. A static site generated from Markdown files and hosted on institutional infrastructure — or simply zipped and deposited in a preservation repository — sidesteps this fragility entirely. CollectionBuilder, Wax, and similar tools are building a new infrastructure for digital collections that treats sustainability as a first-order design constraint, not an afterthought.

The environmental case is emerging too. The Digital Humanities Climate Coalition explicitly recommends static sites for their lower carbon footprint — fewer server resources, less computation per page load, no database queries.

What this means for archivists right now

Markdown won't replace EAD. It won't replace PDF/A for fixed-format preservation. It won't solve the metadata problem on its own. But it has already proven its value as the connective tissue of archival operations — the format for processing manuals, policy documentation, blog posts, digital collections, and institutional knowledge that needs to survive changes in staff, software, and institutional priorities.

The path forward isn't Markdown versus everything else. It's Markdown as part of a deliberate, standards-aware format strategy. Pair it with YAML frontmatter for lightweight metadata. Use Pandoc to convert to and from other formats as needed. Store it in Git for version control. Generate static sites for access. And keep PDF/A in your toolkit for documents that need fixed visual rendering and mandated metadata.

The most preservation-friendly decision any archivist can make is also the simplest: write in plain text. Format it in Markdown. Put it somewhere version-controlled. The rest is implementation detail. Twenty years from now, when the current crop of proprietary platforms has been sunset and migrated and sunset again, those Markdown files will still be sitting there, perfectly readable, waiting for whatever comes next.
